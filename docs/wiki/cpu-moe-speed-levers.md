> Summary: Ways to speed up the big CPU-RAM-resident MoE models (GLM-5.3, GLM-5.3-Flash, Hy4-preview, MiMo-V2.6-Pro) on Jack's dual-Xeon box, distinct from [[v100-speed-frontier]] which is GPU/V100-specific. Read before running or tuning any of these big models.

Researched Sep 22 2026. Hardware: dual Xeon E5-2699 v3 (Haswell, AVX2 only, no AVX-512/AMX), 503 GiB RAM across 2 sockets (~251 GiB/socket), 2x V100 16GB. Companions: local-model-landscape, v100-speed-frontier, and cpu-moe-hardware-anchors (real dual-Xeon measured speeds, the working ik_llama flag set, GSQ-RCO quants — THIS FILE IS AT ITS SIZE CAP, new findings go there).

## RANKED LEVERS

\#1 — SWITCH ENGINE TO ik_llama.cpp (ikawrakow's fork). Biggest lever, real measured numbers on comparable hardware. [MEASURED, community, saood06 on ggml-org/ik_llama.cpp discussion #164] Xeon E5-2683 v4 (Broadwell, AVX2-only — one generation newer than Jack's Haswell E5-2699 v3, same instruction-set ceiling), 70B MoE model: decode 1.54-1.91x faster than mainline llama.cpp, prompt processing ~5.05 vs ~2.70 t/s. After manually repacking to IQ4_XS_R4 (ik_llama.cpp's CPU-optimized repacked quant format), decode reached 6+ t/s from a ~3 t/s baseline — repacking alone is worth roughly another 50-100%+ on top of the engine swap. Separate 8B-model PP-512 numbers on AVX2: IQ3_S 5.2x faster, IQ2_M 4.1x, IQ4_XS 3.6x, even Q8_0/BF16 1.8-3.3x vs mainline. Why the earlier "ik_llama.cpp: NO" verdict in v100-speed-frontier does NOT apply here: that verdict was about running the GPU-resident 27B — ik_llama.cpp's CUDA backend needs Turing+ (sm_75), which V100 (sm_70) fails. These four big models are CPU-only regardless of engine (they don't fit in 32GB VRAM at any usable quant), so the CUDA-architecture gate is irrelevant. ik_llama.cpp's own README: "fully functional and performant compute backends are CPU (AVX2 or better, ARM_NEON or better) and CUDA (Turing or newer)" — the CPU path is unconditional. ARCHITECTURE SUPPORT, checked per model (this is the gate to verify before building):

- GLM-5.3 (full, glm-dsa): SUPPORTED. ik_llama.cpp README lists "GLM-5 (PR 1268)" and a Sep 2026 HF commit note says "GLM-5 support merged into ik_llama.cpp main now" (ubergarm/GLM-5-GGUF). High confidence this covers GLM-5.3 since it shares the glm-dsa base with GLM-5.2/5.
- MiMo-V2.6-Pro (mimo2): LIKELY SUPPORTED. README lists "Mimo-2.5 (PR 1723)"; issue #1720 "Port MiMo v2.5 from mainline" is closed (by that PR). V2.6-Pro is the same total/active param count as V2.5-Pro (same architecture, new RL weights per local-model-landscape), so should load, but UNCONFIRMED for V2.6 specifically — no V2.6 GGUF exists yet to test against.
- Hy4-preview (hy_v4): UNCONFIRMED, likely NOT YET. README only lists an older "Hunyuan (PR 565)" — almost certainly the pre-hy_v4 Hunyuan-A13B architecture (mainline issue #14415), not the new hy_v4 preview arch that merged into mainline llama.cpp Aug31/Sep6. No hy_v4-specific ik_llama.cpp PR found. Check before building for this one.
- GLM-5.3-Flash (glm5next): NOT MERGED. PR #2376 ("model: Add GLM-5.3-Flash (glm5next) runtime support" by Skelectric) is still OPEN as of Sep 1 2026, same unmerged state as mainline. A companion PR #2399 adds MTP/NextN self-speculative decoding for it, also unmerged. FREE CHECK before building: same method as elsewhere in this memory — check ik_llama.cpp's current src/llama-arch.cpp-equivalent for the exact model you want, rather than trusting README name-drops which can be stale.

\#2 — NUMA MIRRORING. Second biggest, but needs an unmerged fork AND 2x RAM. Two independent implementations, neither merged anywhere Jack can pull directly:

- Mainline fork (vproxy-tools/llama.cpp), GGML_NUMA_MIRROR: duplicates full model weights per NUMA node (separate tensor->data pointer per node, thread-local access by NUMA affinity). [MEASURED] QwQ-32B FP16: 6.6 -> 10.7 t/s; DeepSeek R1 671B Q8: 7.2 -> 9.7 t/s. Roughly +60% decode. Not merged into mainline llama.cpp as of the discussion.
- ik_llama.cpp's own --numa mirror fork (discussion #2030, unmerged, ikawrakow open to a PR but wants llama-sweep-bench numbers + cleanup first): [MEASURED] Qwen 122B MoE 1.47x, Gemma 26B MoE ~1.4x, dual-socket R740 weights-mirror 7.75 -> 12.60 t/s (1.63x). Degrades with long context (KV cache also has to cross sockets unless mirrored, which costs even more RAM); "mirror stays at or above single-socket" for the weight-bound (short-context) case, which is most of what these big models will be used for. RAM COST IS THE BINDING CONSTRAINT FOR JACK: mirroring needs the FULL model twice, once per socket (~251 GiB/socket, realistically ~220-235 GiB usable after OS/service overhead). That caps which of the four models can even use this trick: | Model | Smallest quant | Fits one socket for mirroring? | | GLM-5.3 (full) IQ1_S | 202 GiB | YES, comfortably | | GLM-5.3 (full) IQ1_M | 213 GiB | Yes, tight | | GLM-5.3-Flash Q4_K_XL | 186 GiB | Yes (but arch not merged anywhere yet, see #1) | | Hy4-preview IQ1_M | 219 GiB | Borderline/tight | | MiMo-V2.6-Pro IQ1_M | 283 GiB | NO — exceeds one socket, cannot mirror as-is | GLM-5.3 full is the standout: best NUMA-mirror fit AND already has confirmed ik_llama.cpp support (#1), so it's the one model where both levers stack cleanly.

\#3 — PLAIN --numa distribute (free, already in stock llama.cpp, zero build risk). For a model too big for one socket (must span both anyway, like MiMo), community reports (ggml-org discussion #19102) that naive dual-socket use generally UNDERPERFORMS single-socket for anything that fits in one socket's RAM — cross-socket access is the bottleneck, not a bandwidth bonus. For models that genuinely need both sockets' RAM, one reported workaround beats plain single-socket: drop the page cache, then load with --mmap (not --no-mmap) plus --numa distribute, letting the OS migrate pages to the accessing node during warmup — reportedly higher decode than single-socket, at some cost to prompt-processing speed. No hard numbers published for this specific trick. Free to try, worth testing on MiMo-V2.6-Pro once a quant exists, since that's the one model NUMA mirroring can't help. Full recommended flags for the dual-socket-required case: numactl --interleave=all, disable NUMA balancing (echo 0 > /proc/sys/kernel/numa_balancing), --numa distribute.

\#4 — QUANT FORMAT CHOICE. Already partly known from Hy4 research in local-model-landscape: i-quants (IQ1_M, IQ2_XXS etc.) are markedly more compute-hungry to dequantize on plain AVX2 than K-quants, because Jack has no AVX-512. This is BEFORE considering ik_llama.cpp's repacked types. If staying on mainline llama.cpp, prefer K-quants over I-quants at the same size where a choice exists (rarely true at these extreme sizes — the smallest usable files are almost always I-quants because that's what fits). If moving to ik_llama.cpp (#1), its repacked R4/R8 variants (e.g. IQ4_XS_R4) are FASTER than either, per the 3 -> 6+ t/s example above — the highest-leverage single quant change available.

\#5 — HYBRID GPU OFFLOAD OF ATTENTION/SHARED TENSORS. Covered in v100-speed-frontier's "would stopping the 27B help" note — -ot "ffn_.*_exps.*=CPU" pattern moves attention/dense/shared-expert tensors to GPU, leaving only the giant per-token-varying expert FFN weights on CPU RAM. Needs the 27B stopped to free VRAM. Modest expected gain (the non-expert slice is a small fraction of 40-49B active params) — stacks with, doesn't replace, the levers above.

## BOTTOM LINE, STACKED (SPECULATIVE — NOTHING BELOW IS MEASURED FOR JACK'S ACTUAL MODELS)

Engine swap alone (~1.5-1.9x) plus repacked quants (another ~1.2-2x in the one cited example) plus NUMA mirroring where it fits (~1.4-1.6x) could plausibly compound into a 3-5x improvement over the naive mainline-llama.cpp-single-socket estimates in local-model-landscape (which were ~1.3-2.8 t/s). That could mean something like 4-10 t/s instead of 1.3-2.8, for GLM-5.3 (full) specifically, since it's the one model with confirmed ik_llama.cpp support AND a mirror-friendly size. This is arithmetic multiplication of separately-measured numbers from OTHER people's hardware, not a measurement on Jack's box — treat it as a plausible ceiling to test toward, not a promise. RECOMMENDED ORDER IF HE WANTS TO CHASE THIS: (1) build ik_llama.cpp, confirm GLM-5.3 (glm-dsa) loads and benchmark stock single-socket decode first as a clean baseline; (2) try IQ4_XS_R4-style repacked quant if available for GLM-5.3's size class; (3) only then attempt the NUMA-mirror fork, since it's the least mature (unmerged, wants cleanup) and highest-cost (2x RAM) step.

## *** Sep 22 2026 — BROADER PASS: SPACE AND "OTHER" PERFORMANCE, NOT JUST SPEED ***

Jack asked for performance in general — speed, disk/RAM footprint, anything else. New findings beyond the ranked levers above.

### SPACE: shrink the model itself, not just quantize it harder

REAP (Router-weighted Expert Activation Pruning) — a real, separate axis from quantization: removes whole redundant EXPERTS from a MoE model (not bits per weight), evaluated by router-gate value + activation norm. Confirmed example: unsloth/GLM-4.6-REAP-268B-A32B-GGUF prunes GLM-4.6 from 355B to 268B (experts 160->120, a 25% uniform prune, ~24.5% size cut) while "maintaining almost identical accuracy on code/agentic/function-calling" per the card — but that claim is [VENDOR], and the BF16 variant's own eval numbers are marked "TBD" on the card itself, so treat the quality claim as unverified until a third party checks it. Also exists for other models: unsloth/Qwen3-Coder-REAP-363B-A35B-GGUF. REAP work IS actively happening on GLM-5.3-Flash specifically: github.com/patrickbdevaney/glm-5.3-reap, an end-to-end pruning pipeline (96.99% of GLM-5.3-Flash's params are routed experts, i.e. almost the whole model is pruning-eligible), already through two passes with "per-expert healing," measured 0.837 top-1 agreement between pruned student and full teacher on 241,516 held-out tokens. NOT YET USABLE for Jack: no GGUF produced (the repo says GGUF conversion is "downstream, not included") and GLM-5.3-Flash's architecture isn't even merged into llama.cpp/ik_llama.cpp yet regardless (see ranked levers above). Worth checking back on this repo periodically — if it ships a GGUF, that's a genuine free size cut once the architecture lands. No REAP variant found yet for GLM-5.3 (full, glm-dsa), Hy4-preview, or MiMo-V2.6-Pro specifically. Since REAP is a post-hoc technique applicable to any MoE, community REAP'd versions of these may appear later, same as they did for GLM-4.6 and Qwen3-Coder — worth a periodic re-check, not a one-time answer. Distilled small variants — the blunt but real space lever: per earlier MiMo research, Xiaomi released "a 9B distilled variant based on Qwen3.5-9B" alongside MiMo-V2.6. This trades away most of the capability gain for a model that fits ENTIRELY differently on the box (GPU-sized, not RAM-giant). Worth remembering as the honest alternative to chasing the trillion-parameter original: if the task doesn't need frontier capability, a distilled/smaller sibling is a bigger space win than any pruning or quant trick applied to the giant. KV cache quant (already used: q8_0 KV on the 27B): going q4_0 KV instead of q8_0 roughly halves per-token KV cost again, at some quality cost to long-context recall. For the giant CPU models this barely matters for RAM (their KV is small relative to weights per jarvis-model-research's GLM-5.3-Flash KV-budget note — hybrid/sparse-attention architectures already have tiny KV footprints), but does matter for the DENSE-attention parts of glm-dsa/hy_v4/mimo2 if those aren't equally KV-light. UNCONFIRMED per-token KV size for GLM-5.3(full)/Hy4/MiMo specifically — same "measure it, don't guess the constant" rule as the Sep 13 GLM-Flash KV note. mmap-beyond-RAM (niche, high-risk): github.com/dimitripavlov/oversized-moe-runtime claims to run MoE GGUFs LARGER than physical RAM via bounded zero-copy expert residency over mmap — i.e. trading disk I/O for a higher size ceiling than 503 GiB allows. Unofficial third-party fork, unverified, not evaluated further — flagging existence only, this is a last-resort lever if a model is chosen that doesn't fit even with everything else applied.

### OTHER: caching, batching, and a real trap for these specific models

PROMPT/CONTEXT CACHING WILL PROBABLY NOT WORK WELL ON THE HYBRID-ATTENTION MODELS — IMPORTANT CAVEAT. llama.cpp's incremental KV-cache reuse (skip re-processing a shared prefix across turns/jobs) breaks specifically on sliding-window and recurrent/hybrid-state architectures: "advanced cache operations such as removing tokens or shifting positions are not possible when using SWA cache" and recurrent models "maintain a single running state overwritten at each step, making partial truncation impossible" — when the server can't find a valid resume checkpoint it resets to zero and reprocesses the FULL prompt every turn (particula.tech, checked against a Jul 2026 llama.cpp state). Detection: flat time-to-first-token across turns; force the log line with -lv 4, look for "forcing full prompt re-processing due to lack of cache data" (silent at default verbosity 3 — a real gotcha). Consequence per model, since three of Jack's four candidates use non-standard attention:

- GLM-5.3-Flash (glm5next, KDA hybrid linear+sparse): HIGH RISK of this — it's exactly the recurrent-hybrid case the article describes. Every batch job with a shared system prompt could reprocess the whole prefix from scratch. UNCONFIRMED for this specific architecture, worth testing with -lv 4 the moment it's runnable.
- GLM-5.3 (full, glm-dsa): glm-dsa is sparse-attention (DeepSeek-style indexer), NOT the recurrent-state kind per its own description — LOWER RISK, plausibly caches normally, but UNCONFIRMED. This is one more reason GLM-5.3 full is the strongest first candidate: mirror-friendly size (above), confirmed engine support (above), and plausibly normal prompt caching, versus Flash's three open question marks.
- Hy4-preview (hy_v4) and MiMo-V2.6-Pro (mimo2): architecture attention style not established in this memory yet — check before assuming either way. Workarounds if caching is broken: lower --checkpoint-min-step (default 8192) toward the actual per-turn length; avoid mutating the prompt prefix between turns/jobs in whatever harness queues these; --swa-full only helps pure-SWA models, not recurrent-hybrid ones; disk-backed checkpoints (--cache-disk) were still unimplemented as of Jul 2026. BATCH/UBATCH SIZE FOR PREFILL: llama.cpp RFC discussion #23262 claims up to 2x prefill by raising -b/-ub (logical/physical batch size) for prompt processing specifically, in VRAM-constrained cases — same direction as the -b 4096 -ub 4096 recommendation in the MoE offload guide cited above. Decode is unaffected (still bandwidth-bound), this is a prefill-only lever, but worth setting regardless since it's free. SPECULATIVE DECODING BEYOND NATIVE MTP: MIXED EVIDENCE, DON'T ASSUME A WIN. Two cautionary sources: a community RTX 3090 test of Qwen3.6-35B-A3B (unsloth discussion) found speculative decoding net-negative after a recent llama.cpp PR; a dev.to writeup titled "Why MTP doesn't speed up your llama.cpp inference (and how to actually fix it)" makes the same point generally. Counter-evidence: a third-party fork (LaurentZuijdwijk/llama.cpp, adaptive speculative decoding --spec-draft-adaptive) claims 4.7x on structured output and 1.9x mainline prefill on MoE specifically — but it's a personal fork, unmerged, unverified by anyone else. Net: speculative decoding for these CPU MoE models is a maybe, test it on the actual box rather than assuming the GPU-27B's MTP win (32->83 t/s) will repeat. None of GLM-5.3(full)/Hy4/MiMo's native speculative/MTP support has been confirmed working end-to-end on Jack's box yet for any of them. MoE expert cache (VRAM-caches hot CPU experts, hybrid GPU/CPU hit-miss execution): RFC discussion #24528, unmerged (community branch moe-cache-v2-pr by @leloch). Measured +25% decode (GLM-5.1 754B) and +7-57% across other models, but ALL on 2-4x RTX 3090 setups (48-96GB+ VRAM). Explicitly flagged as limited benefit for a 32GB-VRAM box unless the cache can hold 20-30% of expert weights — for Jack's ~200-300GB expert pools that would need 40-90GB of VRAM, far past his 32GB total. Not a near-term lever for Jack unless a future GPU upgrade changes the VRAM math (see gpu-upgrade-options); flagged here so it isn't rediscovered as new later.

### MORE PERFORMANCE LEVERS FOUND THIS PASS

Huge pages (hugetlbfs) — real but for LOAD TIME, not decode speed. llama.cpp issue #12444 claims up to "10x" faster model LOADING (not token generation) for huge models via Linux hugetlbfs, tested against DeepSeek-R1 671B (~377-400GB). Requires manual OS setup: pre-allocate huge pages via sysctl, mount hugetlbfs, copy the model file onto that mount, point llama.cpp's mmap at it there. Not merged as a llama.cpp feature (issue closed/stale, no native flag) — this is a manual OS-level trick, not a build option. Relevant to Jack's own flagged pain point in local-model-landscape (13 min cold load on SATA HDD, 5 min SSD, 1.5-2 min NVMe) — if it works at anywhere near the claimed ratio, it could turn a multi-minute cold start into seconds, which matters for the "swap which giant model is resident" workflow. UNTESTED for Jack's box and quant sizes. bitnet.cpp / T-MAC: checked, does NOT unblock Hy4's stuck STQ1_0 quant. microsoft/BitNet is an inference engine for models NATIVELY TRAINED as 1.58-bit BitNet architectures — it is not a generic backend that can run an arbitrary model's ternary-quantized GGUF (like Hy4-preview's STQ1_0 file, which is a post-hoc quantization of a normally-trained model, a different thing). Rules out this as a path around the still-unmerged AVX2 kernel PR for STQ1_0 on x86. No update found on that PR's merge status this pass (still presumed open, same as the Sep 13-14 notes in local-model-landscape).

## *** Sep 22 2026 (cont'd) — MODEL-SPECIFIC DIGGING: REAL CPU BENCHMARK FOUND, PLUS A MAJOR GLM-5.3 ARCHITECTURE CORRECTION ***

## *** Sep 22 2026 — SPEED CEILING RECOMPUTED FOR THE QUANT JACK ACTUALLY CHOSE (UD-Q4_K_XL). REVISES THE 4-10 t/s PROJECTION DOWNWARD. ***

Jack asked how fast GLM-5.3 can go with zero quality sacrifice, and whether GLM-5.3-Flash could use NUMA mirroring. That constraint removes four of the six big levers in this file: lower quant, q4_0 KV, REAP pruning, and switching models are all off the table. Also removed: repacking to IQ4_XS_R4, because that is a DIFFERENT quant, not a lossless rearrangement. (An ik_llama.cpp run-time repack (-rtr) of the existing Q4_K_XL bits WOULD be lossless and keep the gain — UNVERIFIED whether -rtr supports Unsloth's mixed-type UD quants. Open item.)

### THE GOVERNING ARITHMETIC (use this frame for any model on this box)

Decode is bandwidth-bound: t/s = effective bandwidth ÷ bytes read per token, and bytes/token = active params × bits-per-weight ÷ 8. Only three things beat it: raise effective bandwidth (NUMA), cut bytes/token (GPU offload of non-expert tensors), or emit >1 token per pass (speculative/MTP). Faster kernels help only to the extent the workload is compute-bound, which on AVX2-without-AVX-512 is a real but partial share.

- GLM-5.3 full, UD-Q4_K_XL: 467 GB / 753B = 4.96 bits/weight; 40B active → ~24.8 GB/token. At Jack's measured ~39 GB/s → 1.6 t/s baseline. The previously stored "~2.7 t/s estimate" requires ~67 GB/s effective and is optimistic; realistic unoptimized band is 1.5-2.0 t/s.
- Hardware bandwidth reference: 4ch DDR4-2133 = 68.3 GB/s theoretical per socket, 136.5 GB/s dual; E5 v3 QPI 1.1 at 9.6 GT/s ≈ 19.2 GB/s per link per direction.

### *** Q4_K_XL STRUCTURALLY FORBIDS NUMA MIRRORING FOR GLM-5.3 FULL — AND FORCES A CROSS-SOCKET PENALTY ***

435 GiB of weights vs ~251 GiB per socket. Two consequences Jack had not connected:

- Mirroring needs 2 × 435 = 870 GiB against 503 GiB. Impossible. The mirror lever (~1.5x) is simply unavailable at this quant.
- The model cannot even fit ONE socket, so it is FORCED to span both, meaning roughly half of every token's weight reads cross QPI (~19.2 GB/s/link vs 68 GB/s local). This cross-socket tax is the largest structural drag and cannot be engineered away at Q4. It is a real hidden cost of choosing Q4 over IQ3_XXS, separate from the RAM-headroom tension already noted. NO QUANT OF GLM-5.3 FULL IS BOTH MIRRORABLE AND GOOD. Largest quant fitting one socket is UD-Q2_K_XL (253.9 GB = 236 GiB, 2 copies = 472 GiB, extremely tight before KV) at 80.93% top-1 vs Q4's 94.29%. UD-IQ3_XXS (262 GiB) already exceeds a socket. Mirroring the full model means destroying it. Door closed, cleanly — do not re-derive this.

### REVISED STACK FOR GLM-5.3 FULL, LOSSLESS LEVERS ONLY

| Lever | Multiplier | Basis | | GPU offload -ot "ffn_.*_exps.*=CPU" | ~1.3x | removes ~10B of 40B active from RAM (24.8 → ~18.6 GB/token) AND reads that slice at 900 GB/s; ~6-7 GB VRAM at Q4, fits 32GB once the 27B is stopped | | ik_llama.cpp | 1.3-1.6x | discounted from the measured 1.54-1.91x because part of that gain is compute, not bandwidth | | --numa distribute + mmap + interleave | ~1.1x | no published numbers for the trick; uncertain | STACKED: ~2.5-4 t/s, optimistic ceiling ~5 t/s. This SUPERSEDES the "4-10 t/s" projection earlier in this file, which silently assumed NUMA mirroring was in the stack. Removing that ~1.5x drops the honest range by about a third.

### *** GLM-5.3-FLASH IS THE ONE MODEL WHERE MIRRORING ACTUALLY WORKS ***

Flash UD-Q4_K_XL = 186 GiB. Fits one socket (~251 GiB) with ~65 GiB spare; two copies = 372 GiB against 503 GiB. Mirroring is viable at FULL Q4 quality. Flash has only 18B active at ~5.0 bits = 11.25 GB/token, under half GLM-5.3 full's 24.8.

- Unmirrored (fits one socket, so no QPI penalty even without mirroring): ~3-4 t/s

So Flash-mirrored is ~3-4x faster than GLM-5.3-full-optimized. But it IS a quality trade, not a free win: Flash scores 42 on the Artificial Analysis index vs GLM-5.3 full's 45. ## *** Sep 22 2026 — SPECULATIVE DECODING ON MoE: THE "DIFFERENT EXPERTS PER DRAFT TOKEN" FEAR IS REAL BUT SUB-LINEAR. REVISES THE EARLIER "MIXED EVIDENCE, DON'T ASSUME A WIN" NOTE. ***

The worry: verifying K draft tokens needs the union of experts all K tokens route to, so an MoE could read K× the weights and cancel the win. Confirmed real ("expert scattering", arXiv 2607.12696 on DeepSeek-V3.1: verification latency rises linearly with unique activated experts) but the union grows SUB-linearly because expert routing has strong temporal correlation on natural text. [MEASURED, Cohere blog] "temporal correlation reduces unique experts by 20-31% vs the independence baseline"; at batch size 1 with K=3 the model loads only ~2.5× the experts of a single token, not the naive 3.2-3.6×. MoE shows a NON-MONOTONIC speedup curve (sparsity keeps it bandwidth-bound at higher batch sizes, creating a sweet spot), unlike dense models which decline monotonically. Cohere measured ~1.95× at batch size 1, K=3 — BS=1 is unusually good because fixed per-step overheads amortize across the accepted tokens. EcoSpec (arXiv 2607.12696) reports 1.47-1.62× on MoE (1.62 Qwen3, 1.50 GPT-OSS-120B, 1.47 DeepSeek-V3.1). llama.cpp docs state plainly: "MoEs require long drafts."
