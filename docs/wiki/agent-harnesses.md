## GVS5H — the one that matters, because it is built on HIS exact model

github.com/slee-persis/GVS5H (default branch is master, not main; raw README 404s on main). Code MIT, paper/figures/run-data CC BY 4.0. Paper targeted at ICLR 2027. Method: "ledger-based zero-shot self-orchestration" — training-free. Fresh instances of ONE model decompose the problem and coordinate through a shared filesystem holding a plan, notes and the current solution. A manager creates the plan, breaks it into tasks, keeps notes, and coordinates workers. HEADLINE RESULT, quoted verbatim from the README abstract: "Across nine open and closed-weight models on the 100 latest hard LiveCodeBench problems, the method yields gains of up to 23.2 percentage points on pinned backends... Orchestrated GPT-5.6-Terra reaches 88.0% pass@1 against Fable 5's 90.4% at 19% of the cost, and locally served, open-weight Qwen3.8-27B rises from 69.2% to 92.4%, slightly exceeding Fable 5. Gains are not universal: some models are unchanged or worse. Transcript analysis attributes the gain to decomposition and persistent context." So on Jack's exact model the harness is worth +23.2 points on LiveCodeBench Hard. This is the single best piece of evidence for his "the harness makes a big difference" intuition. THE COST SIDE, from the README's own run command: ESCALATION_CLOUD_MAX_TOKENS=128000, ESCALATION_CLOUD_TIMEOUT=7200 (a two-hour per-call timeout), figure caption says "LCB-100, 5 passes, 128k max tokens, reasoning ON", and --parallel 8. THE ARITHMETIC THAT DECIDES IT ON JACK'S BOX: 128,000 output tokens at his MEASURED 32 t/s is 4,000 seconds = 66.7 minutes for ONE call at the cap. A manager-worker run makes many calls per problem, and --parallel 8 against an llama-server with n_slots 4 divides throughput further. The technique is sound and the gain is real, but it converts directly into wall-clock time on a 32 t/s box. Batch/overnight only, never interactive. PRACTICAL CAVEAT: GVS5H is a benchmark runner, not a product. It ships escalation/run_bench.py --engine multiagent|single --only lcb --lcb 100, wired to LiveCodeBench release_v6. Pointing it at Jack's own repo means adopting the ledger pattern, not installing an app. It needs uv and talks to OpenAI-compatible / anthropic / dashscope / openrouter endpoints via provider prefixes, so a local llama-server should be reachable, NOT yet verified.

### VERIFIED FROM SOURCE Sep 14 2026: GVS5H CAN be pointed at Jack's llama-server

Read codebase/v2-current/escalation/orchestrator.py and multiagent.py directly (raw.githubusercontent, branch master).

- chat() dispatches on a model-name prefix: groq:, claude:, openai:, dashscope:, anthropic:, openrouter:, and falls through to ollama_chat().
- The built-in "local" path is Ollama and is USELESS to Jack: ollama_chat POSTs to {OLLAMA_URL}/api/chat, the Ollama-native endpoint, not an OpenAI-compatible one. Ollama is also broken on V100 since v0.30.0 (issue #16449) per local-model-landscape.
- THE WAY IN IS THE groq: PREFIX. Line 15-16: GROQ_URL = os.environ.get("ESCALATION_OPENAI_BASE", "https://api.groq.com/openai/v1/chat/completions"), and the groq branch calls the generic openai_chat(GROQ_URL, ...). So ESCALATION_OPENAI_BASE is a fully overridable OpenAI-compatible endpoint.
- Corroborating: multiagent.py line 17 defaults MULTIAGENT_MODEL to groq:qwen/qwen3.6-27b, i.e. the authors were already driving a Qwen 27B through that prefix. This is almost certainly how the "locally served Qwen3.8-27B" run was done. WORKING CONFIG for jarvis-1 (UNTESTED, derived from source):

```bash
export ESCALATION_OPENAI_BASE=http://127.0.0.1:8080/v1/chat/completions
export GROQ_API_KEY=dummy              # must be non-empty or it raises; llama-server ignores it
export ESCALATION_GROQ_REASONING=      # MUST be empty-string, see gotcha below
export MULTIAGENT_MODEL=groq:<model id as llama-server reports it>
```

GOTCHA: GROQ_REASONING = os.environ.get("ESCALATION_GROQ_REASONING", "none") and then extra = {"reasoning_effort": GROQ_REASONING} if GROQ_REASONING else None. The string "none" is TRUTHY, so leaving it unset sends reasoning_effort: "none" in the body. Export it as an empty string to suppress the field entirely. THE COST KNOBS, which is how you make this tractable at 32 t/s: MULTIAGENT_MAX_ITERS (default 10), MULTIAGENT_MAX_TASKS (default 12, cap on the live task list), ESCALATION_CLOUD_MAX_TOKENS (the paper used 128000), ESCALATION_CLOUD_TIMEOUT (paper used 7200), MULTIAGENT_WS (workspace root), MULTIAGENT_STRICT_FORMAT (default "auto"). Also --parallel N on the CLI, which should be <= llama-server's n_slots (currently 4), not the paper's 8. ROUGH LOCAL BUDGET, estimate not measurement: ~10 iterations at a few calls each is 20-40 model calls per problem; at 32 t/s and a few thousand output tokens per call that is roughly an hour per problem. Overnight work, which is exactly the slot Jack said he has.

## CORPUS QUESTION RESOLVED Sep 14 2026 — and the answer is that it was the WRONG QUESTION

Asked yet again what documents Jarvis should retrieve from, Jack answered with an outcome, not a source list: "I just want it to be able to give me the most accurate deep research." That settles a thing that has been recorded as "blocked, unanswered" since Sep 13, and it settles it by dissolving it. Two different architectures were being conflated:

- (A) Static RAG — pre-index a fixed document set, retrieve, answer. Answers "what is in my documents." This is what "the corpus blocks the harness" assumed, and it is NOT what Jack wants.
- (B) Agentic deep research — plan queries, search, fetch, read, extract, notice gaps, search again, synthesise with citations. Answers "what is true about X in the world." This is what he wants, and for it the web is the corpus. A static local index is close to useless for topics like his goals list (startups, biology, astrophysics, longevity, consciousness). CORRECTION TO CARRY FORWARD: stop describing the missing corpus as the blocker for research. For architecture B the blocker is search, not storage. The embedding and reranker models still earn their keep, but for ranking chunks of FRESHLY FETCHED pages per query, not for maintaining a pre-built index. COMPONENTS FOR (B), and where Jack stands: search backend to FIND sources — MISSING, and it is the real blocker; fetch and render pages — HAVE IT, and it is good (headed Chrome on Xvfb with a CDP bridge, so JS-heavy pages work); chunk/embed/rerank retrieved text — embedding running, reranker not yet pulled; the multi-step loop itself — not built; citation discipline and a verification pass — prompt-level only, §18. THROUGHPUT REALITY, which mirrors the coding finding exactly: a deep research pass is 5-10 searches and 10-20 page reads. Page reads are PREFILL-heavy, and at his MEASURED 145 t/s prompt a 5,000-token page costs ~34 s just to ingest, so 20 pages is ~11 minutes of prefill before any generation. A real run is 20-60 minutes. Deep research is batch work on this box, not conversational — the same conclusion reached for GLM and for the coding harness. CONSEQUENCE WORTH ACTING ON: the job queue is NOT a coding feature, it is the batch-work substrate. Coding jobs and research jobs are both jobs. Design it generically with a job type field rather than building a coding-only queue and a research-only one. On whether to build SearXNG first, Jack said check what is already configured first rather than assume. Open WebUI's web_search capability is toggled ON in the Jarvis preset; whether a provider is actually configured is unverified. Check Admin Settings → Web Search / the config API before building anything. HONEST CEILING TO STATE PLAINLY WHEN THIS IS BUILT: Jack's preference asks for a blind-agent verification pass and a 95% accuracy bar. A local 27B scoring 34 on AA Intelligence Index v4.3 cannot self-verify to that standard. It will produce confident, well-formatted research that is sometimes wrong, because judging source quality and noticing an unsupported claim is exactly what a mid-size model is weakest at. The loop and the citations make it auditable; they do not make it frontier-accurate.

## AGREED DESIGN, Sep 14 2026 — build ONLY when the server is back up

Jack chose the job-queue version, and explicitly said to build it only once jarvis-1 is running again, not to stage code in advance.

THE DESIGN FACT THAT SHAPES IT: a harness is a job, not a backend. The supervisor is a synchronous proxy (request → router label → forward to slot → stream back), which works because a slot answers in seconds. A GVS5H run is 20-40 model calls over roughly an hour. It cannot sit behind a synchronous /v1/chat/completions that Open WebUI is waiting on: it will time out, and there is nothing to stream during the manager's planning phase. So the coding route must accept the work, return a ticket, and run in the background.

NO CODING MODEL IS NEEDED FOR THIS. GVS5H is Qwen3.8-27B orchestrating ITSELF ("fresh instances of one model decompose problems and coordinate through a shared filesystem"). The 69.2 → 92.4 gain uses the weights already loaded. This is unblocked today, unlike Qwen3-Coder-Next which is still gated on the Gated DeltaNet / sm_70 question in local-model-landscape.

SHAPE AGREED:

- Router stays exactly as it is, cheap and synchronous. A coding label still goes to the 27B for a conversational answer. The routing branch does NOT change the backend.
- Jarvis gets two new tools: submit_coding_job(spec, repo_path) returning a job id immediately, and check_coding_job(id) returning status plus result.
- A small worker service drains the queue one job at a time, running the orchestration with ESCALATION_OPENAI_BASE pointed at llama-server, writes the result, fires ntfy.
- RATIONALE for tools over a routing branch: the model stays conversational and TELLS Jack it is about to queue an hour of work, rather than silently hanging. The day/night split gets decided in conversation instead of guessed by a 1.7B classifier.
- Deployment note: the existing tool server is browser_tools.py on 8090 exposed via tailscale serve --bg --https=8443 8090. Prefer a SEPARATE service (e.g. jarvis_jobs.py on 8091, its own systemd unit, its own tailscale serve --https=8444 8091, registered as a second tool server) rather than appending to the working 8090 file.
- SIZING: cap harness parallelism at 4, matching llama-server's n_slots 4, not the paper's --parallel 8. Start well below the paper's MULTIAGENT_MAX_ITERS=10 and 128k token caps, then measure one real problem end to end rather than estimating.

ENTRY POINT for arbitrary (non-LiveCodeBench) tasks: multiagent_solve(problem_text, spec, log=None, status_out=None, tests=None) at line 412 of codebase/v2-current/escalation/multiagent.py; single_solve at 479 is the one-call baseline for comparison. run_bench.py is a LiveCodeBench harness and is NOT the thing to call for Jack's own repos.

## Pi Harness — real, but a poor fit

ai-sdk.dev/providers/ai-sdk-harnesses/pi. An adapter connecting Vercel AI SDK's HarnessAgent to @earendil-works/pi-coding-agent. Needs @ai-sdk/harness, @ai-sdk/harness-pi, @ai-sdk/sandbox-vercel and a VERCEL_OIDC_TOKEN; runs in the host Node process and treats the sandbox as a remote filesystem/shell. Built-in tools read, write, edit, bash, grep, glob, ls; MCP support; configurable thinking levels. Custom models via \<PREFIX>_API_KEY + \<PREFIX>_BASE_URL. TWO DISQUALIFIERS for Jack: the docs state "Pi does not support structured output" (he needs JSON-constrained output for routing and for the claims/sources/confidence harness), and "Harness packages are experimental". It is also coupled to Vercel Sandbox infrastructure, which fights the fully-local goal.

## The general evidence that harness > model, worth citing to Jack

alexzhang13.github.io/blog/2026/harness/ argues harnesses are compositional generalizers where base Transformers are not: RLMs generalize to "8-32x longer" tasks when trained only on short contexts, "roughly 10x the eval lift with the same train lift over training the underlying Transformer directly", and generalize across domains (Jeopardy → spam detection) where the base Transformer barely improves. Mechanism claimed: the harness keeps each individual model call in-distribution even when the overall task is not. Also live and unread: arxiv 2606.09498 "Self-Harness: Harnesses That Improve Themselves"; arxiv 2603.03329 "AutoHarness: improving LLM agents by automatically synthesizing a code harness"; databricks.com/blog/ai-harness.

## THE GOVERNING CONSTRAINT for any harness choice on this box

Throughput, not capability. At 32 t/s generation and 145 t/s prompt, every extra model call is wall-clock time. A harness that makes 50 calls costs ~50x a single answer. So the selection rule is: interactive work gets a single-call path; multi-call orchestration is reserved for queued batch work where nobody waits. Same split the supervisor in jarvis-orchestrator exists to enforce. The three point at different answers.

### *** SELF-HARNESS: NEW, AND IT OPTIMIZES THE HARNESS ITSELF AGAINST A FIXED MODEL ***

Paper arXiv 2606.09498, "Self-Harness: Harnesses That Improve Themselves" (Hangfan Zhang et al., Shanghai AI Lab, June 2026). *** CODE IS PUBLIC: github.com/qzzqzzb/Self-Harness (Python, official, arXiv badge). *** An earlier read of the arXiv page concluded "no code released" — that was WRONG; the arXiv HTML simply does not surface the repo link. Method, a three-stage loop with weights and evaluator held FIXED: (1) weakness mining — run the model under the current harness, cluster execution traces by verifier-grounded failure signatures; (2) harness proposal — the same model proposes K diverse, minimal edits tied to specific failures; (3) validation — an edit is promoted only if regression testing on held-in AND held-out splits improves without degrading either. MEASURED on Terminal-Bench-2.0, and note the two number sets differ: | model | held-out split (paper) | full benchmark (repo README) | | MiniMax M2.5 | 40.5% → 61.9% | 42.2% → 53.9% | | Qwen3.5-35B-A3B | 23.8% → 38.1% | 18.0% → 36.7% | | GLM-5 | 42.9% → 57.1% | 46.1% → 57.0% | Two of the three are OPEN-WEIGHT models close to Jack's library, which is what makes this relevant where most harness papers use closed frontier models. Unconfirmed: whether its README documents a local / OpenAI-compatible endpoint. Only 13 stars, no releases, thin docs. Treat as a method to copy more than a tool to install.

### AutoHarness — relevant idea, does not qualify

arXiv 2603.03329, "AutoHarness: improving LLM agents by automatically synthesizing a code harness" (Lou, Lázaro-Gredilla, Dedieu, Wendelken, Lehrach, Murphy). An LLM iteratively refines a code harness from environment feedback. Eliminates all illegal moves across 145 TextArena games; 78% of Gemini-2.5-Flash's Kaggle GameArena chess losses were illegal moves; harnessed Flash surpasses the larger Gemini-2.5-Pro. For single-player games it compiles a full policy into code, "eliminating the need to use the LLM at decision making time." But: evaluated only on closed Gemini/GPT models, and no public code found. Directionally supportive, not adoptable.

### *** THE ARITHMETIC THAT DECIDES WHICH MODEL GETS A HARNESS, AND IT REORDERS THE WHOLE LIBRARY ***

A harness multiplies calls: roughly 20-40 model calls per problem. Against measured/estimated decode speeds, for ~30 calls at ~3,000 output tokens each (90,000 tokens): | model | speed | time per problem | verdict | | Qwen3.8-27B (production) | 69 t/s MEASURED | ~22 min | *** THE ONE TO HARNESS *** | | Qwen3.8-Flash-Next | ~16-24 t/s | ~60-95 min | viable overnight | | GLM-5.3-Flash | ~5-8 t/s | ~3-5 h | marginal | | GLM-5.3 full | 1.5-4 t/s | ~6-17 h per problem | NOT VIABLE in a loop | | MiMo-V2.6-Pro | ~2-3 t/s | ~8-12 h | NOT VIABLE in a loop | *** STRATEGIC CONCLUSION: harness the FAST model, not the big one. *** GVS5H takes the 27B to 92.4% pass@1 on LiveCodeBench-hard, which plausibly beats GLM-5.3 answering single-shot, at roughly 40x the speed. ### CONFIG GOTCHAS THAT BLOCK EVERY HARNESS, VERIFIED

- *** llama-server NEEDS --jinja FOR TOOL CALLING. *** llama.cpp's own docs/function-calling.md: function calling is supported "when started w/ --jinja flag." Without it, harnesses get a 500 and an error naming the flag (seen in Zed discussion #39074 and OpenCode issue #1890). Check the live unit in llama-server-live-unit for this flag before blaming any harness.
- Set context to 64k before blaming the harness or the model. That is the repeated guidance across harnesses.
- Aider has a maintenance gap: PyPI aider-chat 0.86.1 Aug 2025, then 0.86.2 Feb 12 2026, still latest on Sep 23 2026. (GitHub Releases misleads here: newest tag is v0.86.0, Aug 2025.) Prefer something maintained.
- Mainstream harnesses confirmed to drive local OpenAI-compatible endpoints: OpenCode, Goose, Cline, OpenHands, Aider, Qwen Code, Kilo Code, Hermes Agent. Goose moved to the Linux Foundation's Agentic AI Foundation (Apr 2026), so it is the best-governed of them.

### WHAT A "HARNESS" MEANS FOR THE NON-LLM MODELS, since Jack said "any models in my library"

No orchestration framework applies to diffusion. The analogue for the video and image models is: use the 27B to expand and rewrite prompts, and a vision model to score outputs and re-roll the bad ones — best-of-N with a verifier, which is the same test-time-compute idea in a different medium. The few-step distill LoRAs in video-generation-v100 are the other half, since they are what makes generating N candidates affordable at all.
