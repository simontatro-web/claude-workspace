- Never run a broad name-pattern kill (pkill -f, killall) against anything matching llama-server, llama-cli, open-webui, or any production service. Before freeing RAM/VRAM by stopping any process: identify each candidate by PID (ps -p \<pid> -o pid,ppid,cmd,etime) and check systemctl status \<name> to see if it's a managed production unit.
- State explicitly which PIDs are targeted and whether any is the production serving process (the one this very chat may be running through).
- Require an explicit yes/no from the user before stopping anything identified as production — never bundle it into a routine "free up RAM" step.
- Prefer sudo systemctl stop \<unit> over pkill/kill for anything systemd-managed, since it's unambiguous about scope.
- Never treat "the model I'm about to download/load" as justification to remove headroom held by the model currently running the conversation — that's self-termination; disclose it as such if it's ever truly necessary.

Hy4 / Tencent STQ1_0 is a NO, and the earlier note was subtly wrong. The stored claim was "no x86 CPU kernel for STQ1_0 yet". The真 situation: STQ1_0 is not in mainline AT ALL. It needs TWO stacked unmerged PRs:

- \#22836 "ggml-cpu : add STQ1_0 ternary quantization with ARM NEON vec_dot kernel" by sjl623 — still OPEN (50 conversation items, 3 commits, +374/-4). This is the base support.
- \#27377 "ggml-cpu : add AVX2 vec_dot kernel for STQ1_0" by layfhaker — still OPEN, opened ~Aug 20 2026, +475/-4, 18 files. Its own summary: #22836 "adds STQ1_0 support but currently falls back to the scalar generic path on x86. This one adds a proper AVX2 ggml_vec_dot_stq1_0_q8_K so 1.25-bit Sherry / Hy-MT models can run with a real CPU kernel on Intel/AMD as well." It removes the x86 #define forcing STQ1_0 onto the generic path. So on Jack's AVX2-only Xeon E5-2699 v3, Hy4 today means building PR-on-PR and still landing on a scalar path unless he also takes #27377. Also live: #28067 (exclude STQ1_0 from Metal mul_mat), #23332 (CUDA STQ1_0 dequant kernel), and a CUDA MMVQ PR. Tell Jack if #22836 merges.

GLM-5.3-Flash #27754 — still OPEN, and merge is NOT close. By danielhanchen (unsloth), 43 commits, into ggml-org:master from unslothai:glm5next/upstream. Carries a maintainer bot warning: "Large changes require prior discussion (e.g. an issue or RFC) and maintainers may not be able to review this PR as-is. REQUIRED FLAGS confirmed from the PR body: NVIDIA_TF32_OVERRIDE=0 (ggml-cuda/common.cuh sets CUBLAS_TF32_TENSOR_OP_MATH unconditionally, so fp32 GEMMs otherwise run at 10 mantissa bits; fixing it moved top-1 agreement 0.896 → 0.9995) and -fa off (build_attn_mha casts the F32 latent to F16 before ggml_flash_attn_ext, which MLA cannot afford). - Smoke tests on ~/glm5-llama.cpp used the EXISTING Qwen3.8-27B GGUF as a CPU-memory-bandwidth proxy (not GLM itself — GLM has not been downloaded yet as of Sep 13). ## Sep 21 2026 (evening) — NEW FAILURE MODE: reasoning-preservation + agentic tool use = runaway context growth

Jarvis, given the new run_host_command tool and asked to set up its own ~/jarvis-memory/ directory, got sidetracked hand-writing a GGUF binary parser from scratch (repeated failed attempts: wrong header offset, wrong string-length type, wrong type enum) instead of using the already-known gguf_dump tool. Each failed attempt plus its multi-minute internal reasoning block accumulated in context because the chat template's reasoning-preservation was ON by default, re-feeding all prior turns' \<think> content into every subsequent turn. Result [MEASURED]: a single response reached 4,666+ generated tokens, generation speed collapsed from the 44-59 t/s baseline to 5.85 t/s. Not a text-repetition loop — legitimate but wasteful work, compounding via reasoning-preservation. Full technical fix and final config: jarvis-speed-tuning. LESSON FOR FUTURE GUARDRAILS: the existing guardrail rules (never pkill, confirm before stopping production) don't cover this failure mode at all — nothing stopped Jarvis from retrying a failing approach dozens of times while burning tokens and slowing itself down. Worth adding to Jarvis's operating manual once rebuilt: (1) prefer known/existing tools over hand-rolling infrastructure (ask Jack or check documented facts before reimplementing something like a GGUF parser), (2) self-monitor context size during multi-step tool use and stop to ask Jack if a single task is running unusually long without resolution, rather than retrying indefinitely. ALSO NOTED: Jack, not Jarvis, manually edited the systemd unit's -c from 8192 to 32768 mid-session without creating a backup first (departure from the backup-before-edit convention used everywhere else today) — worth Jack keeping that convention himself too, not just expecting it of Jarvis.
