## THE CLOSEST WORKING REFERENCE CONFIG — rcriot25, V100 32GB PCIe [SOURCE]

Qwen3.8-27B-Uncensored IQ4_XS, driver 580.159.04, Proxmox+LXC. Result: TG ~45 t/s average (32-65 range), PP 500-700 t/s. Log line shows `tg = 47.78 t/s, tg_3s = 99.27 t/s` — bursts near 100.

```
--n-gpu-layers 99 --cache-ram 32768 --ctx-size 160144 --parallel 2 --kv-unified
--cont-batching --flash-attn on --batch-size 4096 --ubatch-size 512
--cache-type-k f16 --cache-type-v f16
--spec-type ngram-mod,draft-mtp --spec-ngram-mod-n-match 24 --spec-ngram-mod-n-max 64
--threads 8 --split-mode layer
```

Points Jack's current unit gets wrong vs this: no FA, no MTP, `-b` default (his is 2048) vs 4096, `-c 8192` vs 160144, q8_0 KV vs f16, `--threads 36` vs 8, no `--cont-batching`, spec-type single not combined.

- `--spec-type` takes a COMMA-SEPARATED LIST. `ngram-mod,draft-mtp` runs both. Jack tried ngram-mod alone and got nothing; that is not evidence against the combination.
- `--threads 36` on dual Xeon E5-2699 v3 spans two NUMA nodes. rcriot25 uses 8. Untested on Jack's box, cheap to test.
- f16 KV is viable here because only 16 of 64 layers hold a KV cache (hybrid SSM model), so f16 costs little and avoids the FA-required-for-quantized-V guard entirely.

## PREFILL

- Community V100 numbers: PP 500-700 t/s (rcriot25), 464 t/s at 48K (kvmem). Jack measured 300.95 t/s on a 506-token prompt, so there is real headroom.
- Levers: `--batch-size 4096` (his is 2048), `--flash-attn on`, and `--ubatch-size` (rcriot25 keeps 512).
- [SOURCE] llama.cpp discussion #23262 "UBBoost" RFC: a separate, larger ubatch for prompt processing only. Reported 389 -> 539 T/s (+38%) and 121 -> 273 T/s (+125%) in VRAM-constrained cases via `--promptprocessing-ubatchboost-size` etc. RFC, may not be in b11089 — check before recommending.

## DEAD ENDS — do not spend time here

- `-sm tensor` on V100: THIS ENTRY IS SUPERSEDED — see v100-speed-frontier. Issue #27366 is stale (Aug 18 2026, the week a TP fix landed and was reverted). Mainline gates 2-device TP at cc>=700, i.e. Volta IS supported. `-sm row` genuinely does not exist on CUDA.
- ninfer-v100 (geoffwatts) reports 81 tok/s on sm_70 but is single-GPU only; Jack's cards are 16 GB each and a 27B Q4 does not fit on one. Not applicable.
- FA for decode: near zero. fishlikeX/sm70-attn measured 8k decode 29.06 vs stock ~29 on V100. FA is a PREFILL and VRAM win, not a decode win. Still worth building because `--flash-attn on` is in every working config.
- Raising the power cap: see table above.

## CEILING

18.1 GB of weights read per token / 900 GB/s = ~20 ms = ~50 t/s hard ceiling without speculation. Jack measured 28.09 t/s (35.6 ms/token), ~56% efficiency. The 60-70 t/s he remembers, and rcriot25's 99 t/s bursts, are only reachable WITH speculation. Prioritise MTP over every other tuning item.

## VERDICT ON COMBINING SPEC TYPES: DO NOT. MTP ALONE WINS. [MEASURED Sep 21 2026, Jack's box]

NEXT LEVERS, IN ORDER — and note the ordering constraint: after MTP loads, GPU0 sits at ~15,000 of 16,144 MiB, so only ~1.1 GiB is free. Raising `-b` or `-c` grows compute buffers and WILL OOM GPU0 until VRAM is freed first. So: (1) free VRAM by dropping the mmproj (frees 601 MiB of weights + the 4,658 MiB non-FA CLIP softmax workspace ≈ 5.2 GiB) and/or rebuilding with FA on, THEN (2) raise `-b` to 4096 and `-c` well past 8192, THEN (3) test `--threads 8` vs 36 (dual Xeon E5-2699 v3 spans two NUMA nodes).

## *** Sep 21 2026 (late night) — ROOT CAUSE FOUND FOR "chat is extremely slow / freezes": Open WebUI's builtin_tools bundle, NOT llama-server config. FIXED. ***

Jack reported chat responses (not benchmarks) were extremely slow, prefill taking ~20s, and one response ran away to 4,600+ tokens (see the reasoning-preservation incident above, already fixed). After that fix, Jack said it was STILL extremely slow on fresh chats. (2) Checked model.params (num_ctx was wrongly 999,786 vs actual 32768 — fixed that too, real bug but not the main cause) and disabled 5 background task completions (title/tags/follow_up/query.search/query.retrieval via the `config` table) — these DID NOT actually stop firing (confirmed later, see below) and were not the main cause either.

ACTUAL ROOT CAUSE [MEASURED via packet capture, real evidence not inference]: captured the literal HTTP POST body Open WebUI's backend sends to llama-server (tcpdump on host port 8080, filtered by dest 172.17.0.1 = docker0 gateway, since llama-server listens on the host and the container reaches it via host.docker.internal). Body was 25,532 characters, dominated by a `"tools"` array of 37 entries, 24,582 chars. Only 1 of those 37 was Jack's actual run_host_command tool (325 chars) — the other 36 were Open WebUI's own BUILT-IN native tools (get_current_timestamp, calculate_timestamp, ask_user, list/search/query_knowledge_bases, grep/search/query/view_knowledge_files, search_chats, view_chat, search/list/read/update/add/replace/delete memory tools (8 of them), execute_code, search/view/write/replace notes (4), create/update/list/toggle/delete automations (5), search/create/update/delete calendar_events (4)) — injected into EVERY single request regardless of conversation content, because the model's `meta.capabilities.builtin_tools` was `true`. This is a FIXED ~6,100-token tax (24,582 chars / ~4 chars-per-token) on every message before the model reads a single word of the actual conversation. Confirmed by /slots endpoint: task 1155 ended with n_tokens=6796, task 1194 (same convo, 2nd turn) ended n_tokens=7075 — matches the tools-array size almost exactly, not conversation length.

This ALSO explains why `--no-reasoning-preserve`'s earlier runaway-context incident happened so fast, and why a 2-message "hi, what's the GPU temp" conversation looked like it was processing thousands of tokens — the "18 new tokens" figure in journalctl was real (prefix-cache hit against the identical 37-tool block from a DIFFERENT unrelated conversation's slot), but the TOTAL context per turn was genuinely ~7000 tokens of tool definitions the model never needed.

FIX APPLIED [MEASURED, confirmed]: backed up webui.db first (`/app/backend/data/webui.db.bak-20260921-230159` inside the open-webui container), then set `meta.capabilities.builtin_tools = false` for the `jarvis` model row via `sqlite3`/python (UPDATE model SET meta=... WHERE id='jarvis'), then `docker restart open-webui`. Jack chose "whatever makes it maximized speed" when asked whether to keep any built-in tools (memory/notes/calendar/etc.) — he already has a separate filesystem-based memory system for Jarvis (`~/jarvis-memory/`, set up earlier today) making Open WebUI's built-in memory tools redundant for him. VERIFIED post-fix via a second packet capture: request body dropped to 1,273 chars, 1 tool (just run_host_command). journalctl for that same test message: `prompt eval time = 1552.59 ms / 507 tokens (326.55 tokens per second)`, `eval time = 910.29 ms / 40 tokens`, `release: n_tokens = 550` — down from ~6,796-7,075 total tokens per turn to 550. ## *** Sep 22 2026 00:05 — f16 KV IS NOT VIABLE AT -c 32768 --parallel 2. CRASHED WITH CUDA OOM. [MEASURED] ***

Tested the hypothesis that the 10.3 us/token decay slope comes from q8_0 KV dequant cost. Swapped to `-ctk f16 -ctv f16` (backup of the q8_0 unit: `/etc/systemd/system/llama-server.service.q8kv`).

- f16 KV cost, measured: GPU0 10,862 -> 12,732 MiB, GPU1 13,892 -> 15,762 MiB. +1,870 MiB per GPU, +3,740 MiB total, i.e. f16 is ~2x q8_0 as expected. This CORRECTS the earlier note in this file claiming KV at 32768 costs only ~1,088 MiB total — that figure was wrong.
- Left only 622 MiB free on GPU1. Under two concurrent slots the server hit `CUDA error: out of memory`, `ggml_abort`, `code=dumped, status=6/ABRT`, core dump, systemd auto-restart (Restart=always, restart counter 1). Requests in flight died with `RemoteDisconnected`.
