## THE FRAMING THAT DECIDES EVERYTHING BELOW

V100 HBM2 clock is fixed at 877 MHz — one entry in the supported-clocks table, unraisable. Decode is memory-bandwidth-bound; prefill is compute-bound. Therefore every core-clock, power and thermal knob can only move PREFILL. Decode t/s is nearly invariant to all of them. [SOURCE arXiv:1905.11012, V100 DVFS study: raising memory frequency "hardly affects performance… but leads to higher power"]. This is exactly why the earlier measured 175W -> 200W test gave only +5.4%. Always report prefill (pp) and decode (tg) separately — a blended number hides which one moved.

## *** #2: PCIe TOPOLOGY IS A HARD GATE. CHECK BEFORE ANYTHING ELSE. ***

```bash
nvidia-smi topo -m. If the two cards report SYS, they are on different CPU sockets and GPU P2P is IMPOSSIBLE on Haswell — no software fix exists. [SOURCE: NVIDIA's Robert Crovella, dev forums 2018-05-14, R730 (Broadwell) vs R740 (Skylake): "P2P is not supported between the 2 GPUs, because they are on separate CPU sockets, and P2P traffic could not reliably flow over the QPI socket link… This was not typical/available/possible in the broadwell generation."] E5-2699 v3 is Haswell, same QPI limitation. Codes: PIX/PXB/PHB = same root complex, P2P works. NODE = sometimes. SYS = cross-socket = broken. FIX IF SYS: physically move both cards to CPU1_PCIE1 and CPU1_PCIE3 on the ESC4000 G3 — those two stay at x16 (CPU1_PCIE2 and _PCIE4 auto-drop to x8 when 1 and 3 are occupied). Cost: a screwdriver and 20 minutes, zero risk. This barely matters for the current -sm layer (which passes one small activation per layer boundary and tolerates slow interconnect) but it gates the entire tensor-parallel experiment. Verify after: nvidia-smi --query-gpu=index,pci.bus_id,pcie.link.gen.current,pcie.link.width.current --format=csv should show gen 3 width 16 on both.
```

## *** CONFIRMED DEAD ENDS — DO NOT SPEND TIME ***

- DISABLING ECC IS WORTH EXACTLY ZERO ON THIS CARD. [CONFIRMED, NVIDIA V100 PCIe product brief, verbatim: the card has "native support for ECC and has no ECC overhead, both in memory capacity and bandwidth"; Volta whitepaper: "With V100 and P100, ECC can be active without a bandwidth or capacity penalty"]. The 6.25% capacity / ~20% bandwidth ECC tax is a GDDR5 phenomenon (K80, K40, M40); HBM2 has dedicated ECC storage in the stacks. The widely-cited 12.5% figure is njuffa's STREAM measurement on a K20c, constantly misapplied to V100. nvidia-smi -e 0 frees 0 MB and gains 0 bandwidth, and costs you Xid/row-remap telemetry, which on 7-year-old used HBM is the only early warning a stack is dying. Leave ECC ON.
- OVERCLOCKING A V100 ON LINUX IS IMPOSSIBLE. nvidia-settings clock offsets are read-only on datacenter parts (NVIDIA moderator: "the A100 doesn't support overclocking"), Coolbits does nothing, -lmc is a no-op because V100 has one memory clock. The 1530/1597 MHz figures in some GitHub issues are vBIOS supported-clocks-table entries (opportunistic boost ceiling), not overclocks. --auto-boost-default is Kepler/Maxwell-era and does not apply to Volta.
- vBIOS FLASHING FOR >250 W: LIKELY PERMANENT BRICK. DO NOT. nvflashk broke NVIDIA's signature lock but is tested on GeForce 30/40-series only; Volta/GV100 is not a supported target, and no modded V100 PCIe vBIOS corpus exists. The card has no display output and no dual-BIOS switch, so there is no recovery path from a bad flash. Author's own warning: some BIOSes "have absolutely no thermal protections and will let the card melt itself to death." Risking ~100% of a card for ~4% on prefill only. Expected value deeply negative.
- Resizable BAR / above-4G / PCIe ASPM: nothing to gain. Above-4G is already on (or the cards wouldn't enumerate — each needs a 16 GB BAR1 window). There is no ReBAR toggle for V100. ASPM is not enabled on server slots and pcie_aspm=off does not mean what people think (it means "leave untouched").
- nvidia-smi -c EXCLUSIVE_PROCESS: zero performance benefit, and it breaks running llama-bench alongside llama-server. Leave at DEFAULT.
- GGML_CUDA_ENABLE_UNIFIED_MEMORY=1 with 2x V100: MEASURED FAILURE — "token generation and processing speeds drop to a crawl and gibberish is generated" (llama.cpp discussion #18219).
- Cooling: V100 thresholds are 83 C max-operating / 87 C slowdown / 90 C shutdown. Jack runs 37-51 C. Thermals contribute exactly zero throttling; his limiter is the 200 W SW power cap. Skip all fan/shroud hacks. Going to 250 W might reach 65-70 C, still fine.
- llama.cpp PR #27997 (sm70 FA config for DKQ=256/DV=256): DRAFT, UNMERGED, no maintainer review, flagged by a bot for AI-generated content. Opened Aug 30 2026, last activity Sep 3. It does not add sm70 FA (that already works via volta_mma_available); it adds a tuned config case. Claimed +27.84% prefill on Qwen3.8 27B. Do not plan around it landing.
- fishlikeX/sm70-attn fork: +39.9% prefill measured (372.94 -> 521.93 t/s, Qwen3 27B Q4_K_XL at 176k ctx), and the author is honest that decode is unchanged (~29 t/s regardless of context) because decode is weight-bandwidth-bound. Prefill-only, fork maintenance burden.

## *** Sep 22 2026 — WOULD STOPPING THE 27B SPEED UP THE BIG CPU MODELS (GLM-5.3/Hy4/MiMo)? NO, NOT DIRECTLY ***

Jack asked. Answer: decode on those models is DDR4-bandwidth-bound (this file's framing). The 27B runs -ngl 99, fully GPU-offloaded, weights in HBM2 VRAM — it does not consume DDR4 bandwidth whether running or stopped, so there is nothing to reclaim on the axis that actually limits big-CPU-model decode. What DOES free up: VRAM. Currently ~26 GiB used across both cards (GPU0 12,962 + GPU1 13,644 MiB, this session's measurement) / ~6 GiB free; stopping the 27B frees the full ~32 GiB. The one indirect lever: with VRAM free, could offload non-expert tensors (attention, shared/dense layers) of a big MoE model to GPU via -ot "ffn_.*_exps.*=CPU" (same pattern noted in jarvis-model-research for Qwen3-Coder-Next), leaving only the giant expert-FFN weights on CPU RAM. Real llama.cpp technique, but gain is capped by what fraction of the 40-49B active params is non-expert — likely small (single digits to ~10%), NOT a multiplier. UNMEASURED for GLM-5.3/Hy4/MiMo specifically on this box. Also a real use-case tradeoff: stopping the 27B drops the interactive/judge model while the batch job runs.
